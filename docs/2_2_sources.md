# Этап 2.2. Подбор и изучение источников данных

## Тема и задача этапа

Тема проекта: «Исследование банковских и биржевых данных для обнаружения аномалий и паттернов финансовых транзакций».

По пункту 2.2 методички необходимо подобрать и изучить источники по требованиям пункта 3, а также выбрать категориальные и числовые характеристики объекта исследования и факторов влияния. Ниже перечислены четыре источника требуемых типов. В каждом случае отдельно указаны исходные поля и параметры записи. Вычисляемые показатели не засчитываются как исходные характеристики источника.

## 1. Реляционный набор: банковские операции MoneyData

**Источник и формат.** [Bank Transactions Dataset, Mendeley Data](https://data.mendeley.com/datasets/dnxtg6n4rv/1), DOI [10.17632/dnxtg6n4rv.1](https://doi.org/10.17632/dnxtg6n4rv.1). Набор опубликован как XLSX с табличной структурой; в проекте хранится копия исходного файла `data/raw/laramee26openBankTransactionData.xlsx`. На странице источника заявлено более 6 500 анонимизированных розничных операций за семь лет, начиная с июля 2015 года. Лицензия — CC BY 4.0.

**Объект наблюдения:** одна операция по розничному банковскому счёту. Фактические заголовки имеющегося XLSX: `Transaction Number`, `Transaction Date`, `Transaction Type`, `Transaction Description`, `Debit Amount`, `Credit Amount`, `Balance`, `Category`, `Location City`, `Location Country`.

- Категориальные характеристики: `Transaction Type` (вид операции), `Category` (категория), `Location City` (город), `Location Country` (страна).
- Числовые характеристики: `Debit Amount` (списание), `Credit Amount` (зачисление), `Balance` (остаток после операции).
- Время: `Transaction Date`.
- Идентификатор: `Transaction Number`; он не трактуется как количественная характеристика.

Источник непосредственно описывает исследуемые банковские операции. Разделение суммы на списание и зачисление сохранено как в исходной таблице. Отдельного поля валюты в просмотренной схеме нет; валюту нельзя предполагать по месту или описанию операции.

Пример исходной строки из локального XLSX: `Transaction Number=1`, `Transaction Date=25/07/2022`, `Transaction Type=BP`, `Transaction Description=SAVE THE CHANGE`, `Debit Amount=3.11`, `Credit Amount` пусто, `Balance=541.43`, `Category=Savings`, `Location City=Nottingham`, `Location Country=UK`. Это только иллюстрация исходной схемы; пропуски и корректность значений будут исследованы в пункте 2.3.

## 2. Иерархический источник XML: XBRL-отчёт JPMorgan Chase в SEC EDGAR

**Источник и формат.** Официальный архив SEC EDGAR, XBRL instance XML для годовой отчётности JPMorgan Chase & Co., CIK `0000019617`. Пример проверяемой подачи за 2023 год: [карточка подачи SEC, форма 10-K](https://www.sec.gov/Archives/edgar/data/19617/000001961724000225/0000019617-24-000225-index.html); [XBRL instance XML](https://www.sec.gov/Archives/edgar/data/19617/000001961724000225/jpm-20231231_htm.xml). В карточке подачи SEC отдельно перечисляет извлечённый XBRL instance как документ XML. Используется именно этот XML-документ, а не JSON API SEC. Общие сведения SEC об XBRL и форматах опубликованы в [документации EDGAR](https://www.sec.gov/search-filings/edgar-application-programming-interfaces).

**Объект наблюдения:** финансовая отчётность эмитента за отчётный период; внутри XML она представлена набором XBRL facts с контекстами. Для сопоставимой записи отчёта используются значения отдельных фактов при совпадающих эмитенте, периоде, единице измерения и типе контекста. Таким образом, каждая числовая величина остаётся исходным раскрытым фактом, а не вычисленной метрикой.

- Категориальные характеристики: `CIK / entity` (эмитент), `form` (10-K или 10-Q), `taxonomy` (пространство имён/таксономия), `concept` (XBRL-понятие), `unit` (единица измерения), тип контекста (моментное или периодное значение).
- Числовые характеристики отчётности: факты по концептам `Assets` (активы), `Liabilities` (обязательства), `NetIncomeLoss` (чистая прибыль/убыток); для каждого факта также доступно числовое значение и атрибут `decimals`.
- Время: начало и конец периода или дата моментного контекста, дата подачи отчёта.

Поля `Assets`, `Liabilities` и `NetIncomeLoss` относятся к разным исходным XBRL facts, содержащимся в документе; для таблицы отчётности они должны быть выбраны по контексту и единице измерения. Это требует проверки при чтении XML на следующем этапе. Источник характеризует финансовое состояние публичного банка и банковского сектора, но не связан с владельцем анонимизированного розничного счёта. Он рассматривается как внешний фактор, а не как признак конкретного клиента.

## 3. API с JSON: свечи рынка Binance Spot

**Источник и формат.** Публичный REST API Binance Spot, конечная точка `GET https://api.binance.com/api/v3/klines`. [Официальная документация REST API](https://developers.binance.com/en/docs/products/spot/rest-api) указывает, что ответы по умолчанию выдаются в JSON; рыночные данные публичны. Для запроса свечей задаются торговая пара `symbol`, интервал `interval` и, при необходимости, границы времени. Для проекта запрашиваются пары `BTCUSDT`, `ETHUSDT`, `BNBUSDT` с интервалом `1d`; даты начала рядов могут отличаться, это проверяется на этапе 2.3.

**Объект наблюдения:** одна дневная свеча для заданной пары (в выборке предусматриваются несколько торговых пар). Параметры запроса и справочник торговой пары фиксируются вместе с ответом, чтобы категориальные характеристики не терялись, так как массив Binance Klines сам по себе не повторяет имя пары в каждой строке.

- Категориальные характеристики: биржа (`Binance`), тип рынка (`Spot`), торговая пара (`BTCUSDT`), базовый актив (`BTC`), котируемый актив (`USDT`), интервал (`1d`). Пара и активы указываются параметром запроса и справочными сведениями биржи.
- Числовые характеристики из самой записи API: цена открытия `open`, максимум `high`, минимум `low`, цена закрытия `close`, объём базового актива `volume`, объём котируемого актива и число сделок.
- Время: open time и close time в Unix-времени (миллисекунды).

Это источник биржевого рыночного фактора с собственными числовыми наблюдениями; требуемые числовые характеристики не зависят от расчёта доходности или волатильности. BTC/USDT относится к криптовалютному спотовому рынку, поэтому его нельзя описывать как цену акции или традиционную валютную пару. Сопоставление с банковскими операциями будет временным и исследовательским; причинное влияние не предполагается.

## 4. Неструктурированный источник: тексты финансовых новостей

**Источник и формат.** [Financial News Dataset](https://github.com/FelixDrinkall/financial-news-dataset) — корпус из 51 272 статей Yahoo Finance за 2017–2023 годы, размещённый в виде сжатых JSON-файлов. README источника описывает схему записей и лицензию CC BY-NC-SA 4.0. Текст статьи, а не JSON-контейнер, является неструктурированным содержимым.

**Объект наблюдения:** отдельная новостная статья.

- Категориальные характеристики: `source_domain` (домен источника), `language` (язык), `mentioned_companies` (упомянутые тикеры), `related_companies` и `industries` (отраслевые коды); `news_outlet` содержит издателя, если он указан.
- Числовые характеристики, уже присутствующие в записях: компоненты `sentiment.negative`, `sentiment.neutral`, `sentiment.positive`; для упомянутых тикеров могут быть значения `prev_day_price_*`, `curr_day_price_*`, `next_day_price_*`. Эти значения описаны README набора.
- Время: `date_publish` (публикация), а также `date_download` и `date_modify`, когда доступны.
- Неструктурированный текст: `title`, `description`, `maintext`.

Число слов/символов и тематические метки не засчитываются как исходные числовые/категориальные поля: это будут производные характеристики на этапе 2.3. Лицензия запрещает коммерческое использование и требует соблюдения атрибуции и условий распространения производных материалов; в проекте корпус не перепубликуется.

## Сводная проверка требований пункта 3

| Требуемый формат | Источник и зерно | Не менее 3 категориальных характеристик | Не менее 3 числовых характеристик источника | Время |
|---|---|---|---|---|
| Реляционный | MoneyData, одна банковская операция | тип, категория, город, страна | списание, зачисление, остаток | дата операции |
| Иерархический XML | SEC XBRL, один отчёт эмитента за период; значения берутся из вложенных facts | эмитент, форма, таксономия, концепт, единица/контекст | исходные факты Assets, Liabilities, NetIncomeLoss | период факта и дата подачи |
| API → JSON | Binance Spot Klines, одна свеча выбранной пары к USDT | биржа, тип рынка, торговая пара, базовый и котируемый актив, интервал | open, high, low, close, объёмы, число сделок | время открытия/закрытия свечи |
| Неструктурированный текст | Yahoo Finance corpus, одна статья | домен, язык, тикеры, отрасли, издатель | оценки тональности и цены тикера в записи | дата публикации |

В таблице отдельно названы исходные числовые значения. До анализа SEC-файлов в пункте 2.3 следует подтвердить наличие и соответствие нужных фактов, их единицы и контексты; если схема конкретной подачи не даёт требуемых сопоставимых полей, этот набор необходимо заменить до обработки данных. Иными словами, для SEC XBRL подтверждён формат и наличие множества числовых facts, но окончательную пригодность трёх выбранных тегов по конкретным контекстам нужно зафиксировать при фактической выгрузке.

## План интеграции и границы интерпретации

Возможный общий ключ — календарный месяц, поскольку банковские операции, ежедневные биржевые свечи, даты подачи отчётов и публикации новостей имеют временные отметки. В пункте 2.3 сначала проверяются реальные периоды покрытия и частота каждого источника. Если периоды пересекаются, банковские записи можно агрегировать по месяцу, свечи — агрегировать отдельно от уровня цены (например, средние/последние значения и суммарный объём), новости — считать и сохранять как текстовые документы с месячной меткой, а отчётные факты SEC привязывать к периоду/дате публикации. Показатель SEC нельзя использовать до даты подачи отчёта. Неоднородные значения не усредняются друг с другом; несопоставимые даты остаются пропущенными. Агрегирование — это техническая схема объединения, а не доказательство причинного влияния рынка или новостей на транзакции.

## Допустимость данных Kaggle

Наборы Kaggle можно использовать, если у выбранного набора проверены автор/первичный источник, лицензия или условия конкурса, поля, формат и доступность. Kaggle — площадка, а не сам источник данных. CSV/XLSX с подходящими колонками может выступать реляционным набором; загруженный Kaggle JSON-файл сам по себе не заменяет требование API, отвечающего JSON. В текущем варианте для банковских операций оставлен MoneyData с опубликованной лицензией CC BY 4.0 и уже имеющимся исходным файлом; дополнительный набор Kaggle не добавляется, чтобы не дублировать объект исследования.
